# 04 Order lifecycle and execution

## Purpose
This domain turns the transactions of a signed proposal into orders on the custodian/core-banking order-entry system. It then tracks their outcome until a final state and reconciles orders executed outside the WMP. The proposal status is derived from its transactions' statuses.

## Transaction (order) model
- **Operation types**:
  - buy, sell
  - fund subscription (lump sum, "PIC")
  - recurring plan (PAC): initial subscription, additional payment, variation, termination
  - fund redemption, bond redemption, fund switch
  - auction subscription, repo, securities lending, primary-market bond placement
  - opening of a new managed-mandate line
- **Direction**: INVESTMENT / DISINVESTMENT (sign positive/negative).
- **Domain**: SERVICE (generated by the advisory service), PREVIOUS_PROPOSAL (inherited), ACTUAL_OPERATION (reconciled from real orders).
- **Execution venue priority**: regulated market, MTF, other venue.
- **Fields**:
  - product, new product (switch target), CTV, quantity, value date, FX rate
  - holder, IBAN
  - external order id, transaction number
  - flags: switched, ordinary operativity, patrimonial right, appropriate, in-scope
  - AML supervisor and approval
  - execution detail (normal / executed manually)
  - status and status date, notes

## State machine: transaction status
```
PENDING ──send──▶ PENDING_EXECUTION_IN_PROGRESS ──▶ EXECUTED | EXECUTED_PARTIALLY | DECLINED_PARTIALLY | DECLINED | REVOKED | REJECTED | ERROR_REFUSED_BY_MARKET
   │                                   
   ├─▶ PENDING_LIQUIDITY_ERROR       (insufficient cash; retried)
   ├─▶ PENDING_DAILY_LIMIT_ERROR     (daily limit; retried)
   ├─▶ PENDING_MARKET_CLOSED         (retried next session)
   ├─▶ PENDING_SUITABILITY_FAILED    (re-verification failed)
   ├─▶ PENDING_NEW_EXECUTION         (rescheduled)
   ├─▶ SUSPENDED_WAITING_AUTHORIZATION / SUSPENDED_DEROGATION_APPROVAL / SUSPENDED_AML_VERIFICATION / SUSPENDED_MAR
   ├─▶ AML_LOCKED ─unlock─▶ PENDING
   ├─▶ UNAUTHORIZED
   ├─▶ OPERATION_NOT_SUPPORTED       (cannot be sent electronically → manual)
   ├─▶ MISSING_CONTRACT_ERROR        (customer lacks the required contract)
   ├─▶ TECHNICAL_ERROR
   ├─▶ EXECUTED_MANUALLY             (back-office/branch executed it outside)
   ├─▶ EXPIRED                       (proposal validity elapsed)
   ├─▶ DELETED
   └─▶ MISSING_RECONCILIATION        (sent but no matching order found)
```
SUSPENDED_MAR = held for market-abuse (MAR) review.

## Requirements

### REQ-ORD-001 Order dispatch on signature (MUST)
When a proposal is signed:
1. Build the execution helper per transaction: product, venue, enrichment, holder, account.
2. Include the leftovers of earlier proposals that were not yet executed.
3. For switches, send only the switch-out leg. The switch-in is implied.
4. Mark primary-market placements that cannot be sent electronically as EXECUTED_MANUALLY.
5. Filter out operation types the order-entry system does not support (→ OPERATION_NOT_SUPPORTED).
6. Query existing orders at the custodian, so nothing already sent is resent. Match on product, amount and sign → idempotency.
7. Sort transactions: **disinvestments first** so their proceeds fund the investments, then by venue priority.
8. For each investment, run a **liquidity check** against the custodian's available-liquidity service. Disinvestments skip it. If liquidity is short → PENDING_LIQUIDITY_ERROR.
9. Send each order. Map the response outcome to a status: positive/warning → in progress; missing contract; liquidity; market closed; technical.
10. **Derogation check**: if the advisor-set commissions/charges are below the bank minimum (bank and third-party min/max per-mille and fixed), the order needs derogation approval → SUSPENDED_DEROGATION_APPROVAL.

### REQ-ORD-002 Scheduled execution retry (MUST)
- A scheduled job (several times a day) re-processes signed proposals whose transactions are in retryable states (liquidity, daily limit, market closed, new execution) and resends them under the same rules.
- Skipped states are configurable.
- Proposals already processed in the same run are skipped.
- An anomaly processor records failures without stopping the batch.

### REQ-ORD-003 Status verification / reconciliation (MUST)
A scheduled job, with sync/async/classic variants and all-or-group scope:
1. For signed proposals in progress, fetch the order statuses from the custodian and map them to transaction statuses.
2. Recompute the proposal status detail from the transaction statuses.
3. **Re-verify suitability before execution**: if no orders are yet present at the custodian and the proposal is ≥ 7 days from signature (configurable), re-run suitability. Skip it if a successful verification was already done today. If it fails → PENDING_SUITABILITY_FAILED. A technical error leaves the status unchanged.
4. When the proposal reaches an executed status, mark the dossier's suitability record as executed.

### REQ-ORD-004 Proposal validity expiry (MUST)
- A daily job expires proposals beyond their validity window (file 03).
- All their transactions → EXPIRED. Proposal → EXPIRED.
- Do not bump the "status date" on expiry: it keeps the original date for reporting.

### REQ-ORD-005 Manual transaction actions (MUST)
Authorised users can:
- **update a note** on a transaction
- **update the status manually**, e.g. EXECUTED_MANUALLY or DELETED. The proposal status is recomputed.
- **lock or unlock for AML**, which needs the AML supervisor grant and records who approved
- **reconcile** a transaction with an actual order executed outside the WMP, by linking the external order id

When a transaction was suitability-failed, modifying it triggers a new suitability check. If still not suitable → error.

### REQ-ORD-006 Back-office execution dashboard (SHOULD)
A restricted operations dashboard:
- view the orders present at the custodian for a dossier
- list WMP transactions
- force a transaction status
- force a proposal status

It is restricted to a technical-operator grant. Legacy hard-codes user ids; the new BE must use a role.

### REQ-ORD-007 Order lists for advisors (MUST)
- Paged list of transactions/orders across the advisor's visible customers: default last 30 days, with filters (status, type, date, customer, branch, bank) and Excel export.
- Single transaction detail, plus a "base" (lightweight) variant.

### REQ-ORD-008 Extra-WMP operations import (SHOULD)
A daily feed of operations performed outside the WMP on advised dossiers:
- **filtering**: only executed-status records are imported, plus simulations under specific rules; managed-mandate suitability IDs always import
- **reason codes**: each import is stored with a reason code
- **uses**: the imports serve ex-post reporting, suitability evidence and reconciliation

### REQ-ORD-009 Transaction execution details feed (SHOULD)
A daily feed of execution details (price, quantity, fees, execution venue, timestamp) for WMP-originated orders, used for ex-post costs and best-execution reporting.

### REQ-ORD-010 Third-party fund platform orders (SHOULD, [VENDOR])
Orders on funds distributed via an external fund platform are not sent to the custodian. Instead:
- subscription forms are generated and sent to signature (file 05)
- the platform's transaction list is retrieved for status
- a status set marks transactions as failed

Proposal statuses "WMP operations executed / not executed" cover this path.

### REQ-ORD-011 Operation type priority / mapping (MUST)
- Configurable mapping from WMP operation type to the order-entry operation code: nominal vs CTV amount flag and channel.
- Plus an execution-priority ordering table, loaded by feed.

## Data entities (conceptual)
- **Transaction** (see model above), **TransactionEnrichment** (holder, account, venue, primary/secondary, commissions, expenses, PAC params, distribution choice, counterparty), **TransactionExecutionField** (raw order-entry fields), **TransactionAction** (audit of manual actions), **TransactionNote**.
- **ExternalOrder** (custodian order snapshot: id, status, amounts, date).
- **ExtraWmpOperation** (dossier, product, operation, amount, date, reason).
- **TransactionExecutionDetail**.
- **OperationTypeMapping / Priority**.

## Operations (functional)
- List transactions of a proposal. Modify a transaction (action: note / status / AML lock / AML unlock).
- Reconcile a transaction. Change a transaction's status (back-office).
- List transactions for an advisor, plus export. Get a transaction (full or base).
- Back-office: list custodian orders, list transactions, force transaction or proposal status.

## Async
- **Consumes**: `proposal-signed`.
- **Emits**: `order-submitted`, `order-status-changed`, `order-executed`, `order-rejected`, `order-suspended` (reason), `transaction-aml-locked`/`unlocked`, `proposal-status-recomputed`.
- **Jobs**: execution retry (cron, several times a day), status verification (cron), validity expiry (daily), extra-WMP operations import (daily), execution details import (daily).
- **Locking**: the jobs run with a distributed lock (legacy uses ShedLock). In the new BE: one active consumer per proposal (partition key = proposalId).

## External integrations (generalized)
- **Order-entry service** (custodian): submit order; response outcome codes.
- **Order status service**: list orders by dossier, plus order-status domain values.
- **Available liquidity service**: per current account / dossier.
- **Third-party fund platform** [VENDOR]: login, subscription-form PDF, transactions.

## Regulatory drivers
- MiFID II best execution (Art. 27) and order handling (Art. 28).
- Record keeping (Art. 16(6), RTS 2017/565 Art. 72–76).
- MAR (suspicious order holding).
- AML (high-risk customer holds).

## Legacy-specific, do not port
- Hard-coded user ids for the execution dashboard.
- Mainframe numeric status codes. Map them inside the adapter only.
- Duplicate implementations of "match orders already sent" in the batch and in the service.
